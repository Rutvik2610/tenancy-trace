# ADR-003 — Use Azure Functions with Service Bus queues and a transactional outbox

**Original status: Accepted**

**Primary quality attributes:** Performance, resilience, cost.

**Source image:** [page 3](../source-images/adr-page-3.jpg).

## Context
The sandbox provides Azure Functions, Blob Storage, Azure SQL and Azure Service Bus. Reports and summaries take time and must not block requests. Messages must not be lost between database commit and queue send. Report jobs must finish within a five-minute p95 objective.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| A. Synchronous request handling | Simplest | Timeouts, no retry, no status |
| B. App Service or containers plus workers | Familiar | Not in the sandbox selection, more to operate |
| C. Functions with HTTP triggers and queue-triggered workers, outbox in SQL | Matches sandbox, scales to zero, built-in retry/dead-letter | Cold starts, per-invocation timeout, at-least-once delivery |
| D. Durable Functions orchestration | Visible workflow state | Extra concept and learning curve for a three-step job |

## Decision — Option C
Three Function Apps (workflow, evidence, timeline). Three single-consumer Service Bus queues (`tenancy-events`, `report-jobs`, `summary-jobs`). Transactional outbox for event and job messages. Idempotent consumers. A 270-second job deadline stays inside the Functions default five-minute timeout. Resources provisioned with Bicep.

## Consequences

**Positive:** Low idle cost, built-in retry and dead-letter, repeatable environment, measurable p95.

**Negative:** At-least-once delivery means every consumer must be idempotent. Cold starts add latency. Workers and the Timeline API share one Function App, so a noisy worker can affect the API.

**Evolution:** Split workers into their own Function App or move to Durable Functions if workflows grow.

## Trade-off
Operational simplicity and cost versus latency predictability.
