# ADR-001 — Use bounded, human-reviewed AI summarization behind deterministic validation

**Original status: Proposed** — becomes Accepted when the mentor approves the scope change in writing. **Do not mark Accepted without evidence of approval.**

**Primary quality attributes:** Trustworthiness, availability, accountability.

**Source images:** [page 1](../source-images/adr-page-1.jpg), [page 2](../source-images/adr-page-2.jpg).

## Context
Users want a plain-language summary of a long evidence report. A language model can write one, but it can invent facts, drop labels such as *disputed*, or imply liability. The product must not decide liability, interpret tenancy law, or share anything on its own. The success metric (report within 5 minutes) applies to the deterministic report.

## Decision drivers
Trust in the evidence record, no legal conclusions, availability when AI is down, cost control, testability.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| A. No AI | Simplest, no risk | No plain-language output; no AI/ML domain coverage |
| B. AI writes the report | Fluent | Evidence record becomes non-deterministic and unauditable |
| C. AI summary inside the report job | One step for the user | Report latency and availability depend on the model |
| D. Deterministic report first, separate optional AI summary, code-based validation, human approval | Evidence stays deterministic; AI failure is harmless; output is checkable | More components; summaries may be rejected |

## Decision — Option D

- The report is built from a fixed template and is the source of truth.
- A separate Summary Worker runs only after the report is `Ready` and only when a user requests it.
- The model receives only minimised report content and returns statements that cite event IDs.
- A deterministic Summary Validator checks schema, citations, preservation of status labels, numbers and dates against the source, and a liability/legal-wording deny-list. It rejects rather than repairs.
- Summaries start as drafts. Only the requester can approve. Only approved summaries are visible to others.
- Model, prompt version, source report hash, summary hash and approver are written to the ledger.
- The model is behind an AI Gateway port with timeout, retry, circuit breaker, token cap and per-tenancy daily limit.

## Consequences

**Positive:** The evidence record never depends on a model; AI outages do not affect reports; outputs are traceable and testable; cost is bounded.

**Negative:** Extra components and queue; some fluent summaries will be rejected; validator rules require maintenance.

**Risks:** Text inside events may attempt prompt manipulation (mitigated by delimiting, validation and human review). A validator cannot prove a summary is complete, so the label "AI-generated draft" and review step remain necessary.

## Trade-off
Summary usefulness versus factual risk. Chosen compromise: optional, validated, labelled and reviewed.
