# ADR-004 — Use a pluggable Scan Gate with inline validation for the MVP

**Original status: Accepted**

**Primary quality attributes:** Security, feasibility.

**Source images:** [page 3](../source-images/adr-page-3.jpg), [page 4](../source-images/adr-page-4.jpg).

## Context
Uploaded files are untrusted (trust boundary TB3). The scope sheet mentions malware-scanned storage. The sandbox selection does not include a managed malware scanner, Event Grid or virtual machines.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| A. No scanning | Easiest | Unprotected boundary |
| B. Managed malware scanning on storage | Best coverage | Not in sandbox selection |
| C. Self-hosted antivirus container or VM | Real scanning | Needs compute not selected; high effort |
| D. Scan Gate port with inline validation adapter now, managed scanner adapter later | Works in sandbox, honest about coverage, replaceable | Inline validation is not antivirus |

## Decision — Option D
The inline adapter enforces an extension and MIME allowlist, magic-byte check, size cap (25 MB), blocking of executable and script types, and a test-signature check. Rejected files are never stored and a rejection record is appended to the ledger. A managed scanner adapter that quarantines first and promotes after a clean result is documented as the production design.

## Consequences

**Positive:** TB3 has a real, testable control. The port makes the production upgrade a swap, not a redesign.

**Negative:** Known malware that passes type checks would not be caught in the MVP.

**Risk:** Scope-sheet wording "malware-scanned" overstates the MVP. Align wording with the mentor so it says inline validation for the MVP.

## Trade-off
Scan strength versus sandbox and timeline constraints.
